# AshJobs Library - Architecture Summary

**Date:** 2025-10-14 **Status:** Ready for Breakdown Phase

---

## What We're Building

**AshJobs** is an Elixir library that dramatically simplifies background job
workflows in Ash applications by providing a declarative DSL that transforms
~200 lines of boilerplate into ~30 lines of clean, maintainable code.

### Core Value Proposition

Transform complex multi-step background workflows from this:

```elixir
# OLD PATTERN: ~35 lines per step
update :analyze_messages do
  accept []
  require_atomic? false
  change AnalyzeMessages
  change run_oban_trigger(:send_confirmation)
end

update :handle_analysis_error do
  argument :error, :map, allow_nil?: false
  accept []
  require_atomic? false
  change HandleAnalysisError
end

trigger :analyze_messages do
  action :analyze_messages
  where expr(state == :pending and type == :message_move and substate == :pending)
  on_error :handle_analysis_error
  queue :message_processing
end
```

Into this:

```elixir
# NEW PATTERN: ~8 lines per step
step :analyze_messages do
  action :analyze_messages
  on_success :send_confirmation
  on_error :handle_analysis_error
  queue :message_processing
end
```

**Reduction:** ~75% less boilerplate while maintaining full functionality.

## Architecture Overview

### Design Philosophy

**Simple, Explicit, and Pragmatic**

- **No over-engineering:** Direct integration with ash_state_machine and
  ash_oban (no adapter layers)
- **No unnecessary instrumentation:** Users can add telemetry to their own
  actions if needed
- **Proper separation:** Transformers modify DSL, verifiers validate
- **Leverage existing infrastructure:** Oban handles timing and error tracking

### Core Components

```
lib/ash_jobs/
├── ash_jobs.ex                    # Main Spark.Dsl.Extension
├── dsl/
│   ├── sections.ex                # Workflow section (singular)
│   └── entities/step.ex           # Step entity schema
├── transformers/
│   ├── integrate_state_machine.ex # Generate state_machine DSL (if not exists)
│   ├── integrate_oban.ex          # Generate Oban triggers (if not exists)
│   └── generate_error_actions.ex  # Generate error handler actions
├── verifiers/
│   └── validate_workflow.ex       # Verify actions exist with proper changes
├── info.ex                        # Spark.InfoGenerator
└── helpers.ex                     # Operational functions
```

**Total:** ~7 core implementation files (down from initial 16+)

## Key Technical Decisions

### 1. One Workflow Per Resource

**Rationale:** Aligns with ash_state_machine's limitation of one state machine
per resource.

**Pattern:** Use separate job resources (e.g., `FulfillmentJob`, `ReturnJob`)
rather than multiple workflows on one domain resource.

```elixir
# Domain entity - just business data
defmodule MyApp.Orders.Order do
  use Ash.Resource
  # Business attributes only
end

# Workflow resource - one workflow per resource
defmodule MyApp.Orders.FulfillmentJob do
  use Ash.Resource,
    extensions: [AshJobs, AshStateMachine, AshOban]

  workflow do
    step :load_order do
      action :load_full_order
      on_success :validate_inventory
      on_error :handle_load_error
    end
    # ... more steps
  end
end
```

### 2. Sequential Execution Only (v0.1.0)

**Rationale:** Solves 80% of use cases with 20% of complexity.

**Pattern:** Explicit routing via `on_success`/`on_error`.

```elixir
step :validate_inventory do
  action :check_inventory
  on_success :calculate_total    # Next step on success
  on_error :notify_inventory_error  # Error handler
  queue :inventory_processing
end
```

### 3. Verification + Injection with Warnings

**Rationale:** Make workflow mechanics explicit and visible to users. Provide
great out-of-box experience while being educational.

**What We Generate:**

- **Error handler actions** - Fully generated boilerplate (just state
  transitions and triggers)

**What We Verify & Inject:**

For each user-defined workflow action (on_success actions):

1. Action must exist (user defines it with their business logic)
2. Must have state transition:
   `change {AshStateMachine.Transition, to: :next_step}`
3. Must have Oban trigger:
   `change {AshOban.RunObanTrigger, trigger: :next_step}`

If state transition or trigger is missing:

- ✅ Automatically inject them
- ⚠️ Show warning with exact code to add manually

**Benefits:**

- **Explicit** - workflow mechanics visible in user's code
- **Educational** - warnings teach users the proper pattern
- **Great UX** - works out of box even if user forgets changes
- **No magic** - users see exactly what's needed

### 4. State Attribute Generated by ash_state_machine

**What AshJobs Does:**

- Configures the `state_machine` DSL section
- ash_state_machine extension generates the `:state` attribute based on this
  configuration

**What ash_state_machine Generates:**

- **State attribute** (`:state` by default) - tracks current workflow step

**What Oban Tracks:**

- **Timing & errors** - started_at, completed_at, errors in Oban's jobs table

**Rationale:** Don't duplicate what existing libraries already provide. AshJobs
configures the state_machine DSL, and ash_state_machine handles attribute
generation. Users can query job status via Oban's API or AshJobs helper
functions.

### 5. No Adapter Pattern

**Rationale:** We know the library authors, breaking changes aren't a concern.

**Approach:** Direct integration with ash_state_machine and ash_oban.

**Benefits:**

- Simpler codebase
- Easier to understand
- Less indirection

### 6. No AshJobs Telemetry (v0.1.0)

**Rationale:** Ash and Oban already provide comprehensive telemetry events. No
need to duplicate their instrumentation.

**Existing Telemetry:**

- Ash emits telemetry for all action executions
- Oban emits telemetry for all job lifecycle events

**Future:** May add workflow-specific telemetry in v0.2.0+ if needed for
specialized observability beyond what Ash and Oban provide.

### 7. Proper Transformer vs Verifier Separation

**Transformers** (modify DSL):

- `IntegrateStateMachine` - Generate state_machine DSL (if not already defined)
- `IntegrateOban` - Generate Oban triggers (if not already defined)
- `GenerateErrorActions` - Generate error handler actions (simple state
  transitions)

**Verifiers** (validate):

- `ValidateWorkflow` - Verify all workflow actions exist and have proper state
  transitions + Oban triggers

**Rationale:**

- Transformers only add what's missing (flexible)
- Verifiers ensure workflow mechanics are explicit
- Warnings guide users to add changes themselves

## Generated Code

### DSL Example (User Writes)

```elixir
defmodule MyApp.Orders.FulfillmentJob do
  use Ash.Resource,
    extensions: [AshJobs, AshStateMachine, AshOban]

  workflow do
    step :load_order do
      action :load_full_order
      on_success :validate_inventory
      on_error :handle_load_error
      queue :order_processing
    end

    step :validate_inventory do
      action :check_inventory
      on_success :create_shipment
      on_error :notify_inventory_error
      queue :inventory_processing
    end

    step :create_shipment do
      action :create_shipment
      on_success :completed
      queue :shipping_processing
    end
  end

  attributes do
    attribute :order_id, :uuid
    attribute :order_items, {:array, :map}
  end

  actions do
    update :load_full_order do
      change LoadOrderItems  # User's business logic
      change {AshStateMachine.Transition, to: :validate_inventory}
      change {AshOban.RunObanTrigger, trigger: :validate_inventory}
    end

    update :check_inventory do
      change ValidateInventory  # User's business logic
      change {AshStateMachine.Transition, to: :create_shipment}
      change {AshOban.RunObanTrigger, trigger: :create_shipment}
    end

    update :create_shipment do
      change CreateShipment  # User's business logic
      change {AshStateMachine.Transition, to: :completed}
    end
  end
end
```

### What Gets Generated

AshJobs transformers check if DSL sections already exist before generating them,
allowing users full flexibility to define things themselves.

**1. State Machine DSL (if not already defined):**

```elixir
state_machine do
  initial_states [:load_order]
  default_initial_state :load_order
  state_attribute :state

  transitions do
    transition :to_validate_inventory,
      from: :load_order,
      to: :validate_inventory

    transition :to_create_shipment,
      from: :validate_inventory,
      to: :create_shipment

    transition :to_completed,
      from: :create_shipment,
      to: :completed
  end
end
```

**Note:** The state attribute itself (`:state`) is generated by
ash_state_machine based on the state_machine DSL configuration above.

**2. Oban Triggers (if not already defined):**

```elixir
oban do
  triggers do
    trigger :load_order do
      action :load_full_order
      where expr(state == :load_order)
      on_error :handle_load_error
      queue :order_processing
    end

    trigger :validate_inventory do
      action :check_inventory
      where expr(state == :validate_inventory)
      on_error :notify_inventory_error
      queue :inventory_processing
    end

    trigger :create_shipment do
      action :create_shipment
      where expr(state == :create_shipment)
      queue :shipping_processing
    end
  end
end
```

**3. Error Handler Actions (always generated):**

```elixir
# Simple actions that just transition to error state
update :handle_load_error do
  argument :error, :map, allow_nil?: false
  accept []
  require_atomic? false
  change {AshStateMachine.Transition, to: :failed}
end

update :notify_inventory_error do
  argument :error, :map, allow_nil?: false
  accept []
  require_atomic? false
  change {AshStateMachine.Transition, to: :failed}
end
```

**4. Verification & Automatic Injection with Warnings:**

The `ValidateWorkflow` verifier checks that all user-defined workflow actions
have:

- State transition: `change {AshStateMachine.Transition, to: :next_step}`
- Oban trigger: `change {AshOban.RunObanTrigger, trigger: :next_step}`

If missing, AshJobs automatically injects them and shows a warning:

```
[warning] Action :load_full_order is missing required workflow changes.
Added automatically, but you should add them yourself:

  update :load_full_order do
    change LoadOrderItems
    change {AshStateMachine.Transition, to: :validate_inventory}
    change {AshOban.RunObanTrigger, trigger: :validate_inventory}
  end
```

This provides great out-of-box experience while teaching users the proper
pattern.

## Evolution History

### Initial Proposal (Over-Engineered)

- 16+ files
- Adapter pattern (4 files)
- Telemetry instrumentation
- 5 transformers for validation

### After User Feedback (Simplified)

- ~7 core files
- Direct integration (no adapters)
- No AshJobs telemetry (Ash and Oban already provide)
- 3 transformers + 1 verifier (proper separation of concerns)
- ash_state_machine generates state attribute (AshJobs just configures DSL)
- Verification + injection with warnings (great UX + educational)

### Key Simplifications

1. **"wtf are the adapters for?"** → Removed adapter abstraction layer - direct
   integration with ash_state_machine and ash_oban
2. **"we don't need telemetry"** → No AshJobs telemetry - Ash and Oban already
   provide comprehensive telemetry
3. **"shouldn't these be verifiers?"** → Consolidated validation into single
   verifier
4. **"Oban has that tracking"** → Removed started_at, completed_at, last_error
   attributes - Oban's jobs table tracks these
5. **"ash_state_machine will do that"** → AshJobs configures state_machine DSL,
   ash_state_machine generates the state attribute
6. **"make workflow mechanics explicit"** → Verification + injection with
   warnings approach - error handlers fully generated, user actions verified and
   injected if needed with educational warnings
